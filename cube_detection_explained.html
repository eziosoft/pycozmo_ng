🤖 How Cozmo Cube Detection Works

A step-by-step guide to the vision pipeline that lets Cozmo find and track its light cubes.

Source: Reverse-engineered from libcozmoEngine.so (ARM 32-bit) using Binary Ninja + radare2. This is the actual code running on Cozmo's Android brain, not the pycozmo Python reimplementation.

📋 Overview

Cozmo's cube detection runs at ~30 FPS on a dedicated vision thread. Each frame goes through a pipeline that transforms a raw camera image into 3D cube positions. The system uses custom fiducial markers (not standard ArUco) with a decision-tree classifier and template matching.

┌─────────────────────────────────────────────────────────────────┐ │ VISION PIPELINE PER FRAME │ ├─────────────────────────────────────────────────────────────────┤ │ 1. Camera Image → Grayscale │ │ 2. CLAHE Enhancement (contrast boost) │ │ 3. Rolling Shutter Correction (if moving) │ │ 4. Marker Detection (the core magic) │ │ 5. Pose Estimation (SolvePnP) per marker │ │ 6. Cube Fusion (combine faces → 3D cube pose) │ │ 7. Visibility Check (is cube actually visible?) │ │ 8. Output: 3D cube positions in camera frame │ └─────────────────────────────────────────────────────────────────┘

🔍 Step-by-Step Breakdown

1 Get Camera Frame & Convert to Grayscale

The vision system receives a 320×240 RGB image from Cozmo's camera. It immediately converts to grayscale — color isn't needed for marker detection.

ImageCache::GetGray() → 320×240 uint8 grayscale image
2 CLAHE Contrast Enhancement

Before detection, the image gets CLAHE (Contrast Limited Adaptive Histogram Equalization). This boosts local contrast so markers are visible in both bright and dark areas.

  • Tile size: 4×4 pixels
  • Clip limit: 32 (prevents over-amplification of noise)
  • Applied to the full grayscale image
This is why Cozmo can detect cubes in varied lighting — CLAHE normalizes the image locally.
3 Rolling Shutter Correction (Optional)

If Cozmo's body is rotating fast, the camera's rolling shutter distorts the image (top rows captured at different time than bottom). The system computes per-pixel shifts and warps the image to compensate.

  • Enabled via flag at VisionSystem+0x50
  • Uses RollingShutterCorrector::ComputePixelShifts()
  • Critical for accurate pose when robot is turning
4 🎯 Core: Marker Detection

This is the heart of the system. Cozmo uses a custom fiducial marker detector (NOT standard ArUco) built in the Anki::Embedded namespace.

Detection Modes (3 passes max):

  • Mode 0 (Single): One pass, primary marker set
  • Mode 1 (Alternate): One pass, different marker codes
  • Mode 2 (Dual): Two passes, different marker families

The Detection Pipeline:

Grayscale Image →
Thresholding & Edge Detection →
Find Quadrilateral Contours →
Perspective Warp to 32×32 Patch →
Decision Tree Classification →
Exhaustive Template Matching →
Sub-pixel Corner Refinement →
Bright/Dark Validation →
Valid Marker Detections

Key Components:

📦 VisionMarker

  • 32×32 bitmap template
  • 4 corner positions
  • Validity code
  • Serialized for storage

🗃️ VisionMarkerImages

  • Database of all markers
  • FixedLengthList (embedded-friendly)
  • Loaded from assets at startup

🌳 FiducialMarkerDecisionTree

  • Binary decision tree
  • Samples "probe" pixels
  • Classifies marker type fast
  • Verify step validates

💾 MemoryStack

  • Stack allocator (no heap!)
  • 3 stacks per detection
  • 1 MB limit each
  • Deterministic, fast
5 Pose Estimation (SolvePnP)

For each detected marker, the system computes its 3D pose using PnP (Perspective-n-Point).

  • Input: 4 known 3D corners (canonical) + 4 detected 2D corners
  • Algorithm: cv2.SOLVEPNP_IPPE_SQUARE (fast, stable for planar squares)
  • Output: Rotation vector (rvec) + Translation vector (tvec)
  • Validation: Reprojection error < 3 pixels; face normal must point toward camera
Each cube face is a KnownMarker with pre-defined 3D corners. The engine stores _canonicalCorners3d for each marker type.
6 Create ObservedMarker

Each successful detection becomes an ObservedMarker with:

  • code_id: uint16 (0–17 for cube faces, others for charger/arrow/SDK)
  • marker_type: reference to marker family (wall/top/bottom)
  • quad_2d: 4 corner positions in image (float, sub-pixel)
  • camera: intrinsics for this frame
  • rotation: 0°, 90°, 180°, or 270° (which way the marker is rotated)
7 Cube Fusion (Combine Faces → Cube Pose)

One cube has 6 faces. Multiple faces may be visible at once. The CubeFusionTracker fuses them into a single cube pose.

Single Face Visible:

  • Cube center = face position ± half_cube_size along face normal
  • Cube rotation = face rotation corrected to canonical cube orientation

Multiple Faces Visible:

  • Position: Weighted average of computed centers (weight = confidence²)
  • Rotation: Use highest-confidence face (averaging rotations is mathematically wrong on SO(3))
  • Confidence: Quadratic weighting (dominant face wins)
8 Visibility Check (IsVisibleFrom)

Before reporting a cube, the engine verifies it's actually visible:

  • Project 3D corners to 2D — all must be in FOV
  • Face normal must point toward camera (dot product < 0)
  • Distance within [min_dist, max_dist]
  • Not occluded by other known objects

Failure reasons: BehindCamera, OutsideFOV, WrongOrientation, TooClose, TooFar, Occluded

9 Output: 3D Cube States

The final result per frame is a dict of cube states in camera frame:

  • position: [x, y, z] in mm (X=right, Y=down, Z=forward)
  • rotation_matrix: 3×3 (cube orientation)
  • confidence: 0.0–1.0
  • num_faces: how many faces contributed
  • rotation_source: which face determined rotation (e.g., wall_90deg)
World-frame positions and temporal smoothing happen later in WorldMap (separate module). This pipeline only does per-frame camera-frame detection.

🎲 Marker Types (What Cozmo Actually Detects)

The engine has a fixed set of marker types hardcoded in .rodata:

🎁 Light Cubes (18 markers)

  • 3 cubes (I, J, K) × 6 faces each
  • Faces: BACK, BOTTOM, FRONT, LEFT, RIGHT, TOP
  • Each face has unique marker code

🤖 Robot/Charger (4 markers)

  • MARKER_ARROW
  • MARKER_BULLSEYE2
  • MARKER_CHARGER
  • MARKER_STAR5

📱 SDK Custom (16 markers)

  • MARKER_SDK_2-5 × {CIRCLES, DIAMONDS, HEXAGONS, TRIANGLES}
  • User-defined markers

❓ Special

  • MARKER_UNKNOWN
  • MARKER_INVALID

🔑 Key Takeaways

  1. It's not ArUco. Cozmo uses a custom fiducial system with decision trees for fast classification.
  2. CLAHE is essential. Without it, markers fail in shadows or glare.
  3. Rolling shutter matters. Fast rotation distorts the rolling-shutter camera; correction fixes pose.
  4. Fusion = weighted average + best rotation. Position averages all faces; rotation picks the most confident face.
  5. All per-frame. No temporal filtering in the detector — that's in WorldMap.
  6. Embedded-friendly. Stack allocator, fixed-size containers, no dynamic allocation during detection.
